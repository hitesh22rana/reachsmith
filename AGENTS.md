# AGENTS.md

Follow `MEMORY.md`: it holds durable user preferences.

`SPECS.md` is the source of truth: read it before coding. Per-feature build prompts live in `docs/features/<name>/SPEC.md` (`docs/README.md` maps build order).

## Stack
- Next.js App Router + TypeScript, Tailwind + shadcn/ui, Drizzle on managed Postgres, Better Auth, Valibot validation, TanStack Query, BullMQ + Redis suggestion worker. See `SPECS.md` §5.

## Repository layout
- `app/` contains thin route entry points and route handlers; domain code lives in `features/<name>/`. See `SPECS.md` §12.
- `features/<name>/index.ts` exports public UI; server-only logic has a separate entry point. `components/ui/` holds shared primitives; `lib/` holds cross-feature framework setup and helpers. `proxy.ts` at the root is the cross-cutting request interceptor; `middleware.ts` is deprecated in Next 16.
- `db/` contains Drizzle schema and client; `drizzle/` contains migrations. Add `lib/queues/` and standalone `workers/` with the email pipeline.
- Env via `.env`: database URL, Redis URL, Better Auth secrets.

## Constraints agents miss
- Auth = Better Auth only. No NextAuth, no hand-rolled sessions. Every domain row carries `user_id` from the session.
- SECURITY is non-negotiable: every query filters by session `user_id`; every `:id` route re-checks ownership (404 on mismatch, never 403); never trust client-supplied `user_id` or nested `target_id`/`template_id`; workers re-verify ownership from DB before writing. App queries are the first layer; Postgres RLS is the second, and it is live: every domain query goes through `forUser(userId, ...)` in `db/index.ts` or `asUser(userId, ...)` in `workers/db.ts`, never a bare client.
- Two database roles, not one. `DATABASE_URL` is the owner (migrations, DDL); `APP_DATABASE_URL` is the runtime role and must be a non-superuser without `BYPASSRLS`, because a superuser ignores RLS outright and `FORCE ROW LEVEL SECURITY` does not apply to it. `getDb()` throws at startup if the runtime role can bypass RLS, so a misconfigured deploy fails closed rather than silently serving other tenants' rows.
- Validate at trust boundaries with feature-owned Valibot schemas (`features/<name>/validation.ts`) and shared `parseBody` (`lib/validators.ts`); forms use react-hook-form with the Valibot resolver; client data flows through TanStack Query, server components fetch directly.
- Cross-cutting request concerns (CSRF origin check) live once in `proxy.ts` via `lib/csrf.ts`; per-tenant authn/authz stays in each handler: every route calls `getUserId()` itself. A Server Action posts to its page route, so it bypasses the `/api` matcher and must check origin itself.
- No server-side LinkedIn scraping (ToS). Enrichment = manual input + compliant APIs only (`SPECS.md` §6.2, §10).
- Outreach sending is manual in MVP: generate message, copy to clipboard, mark `sent`. No Gmail/Outlook sync, no `send-email` worker yet (`SPECS.md` §3.5, §8.1).
- Keep Postgres enums (Drizzle pgEnum) exactly as specced: `source_type`, `enrichment_status`, `channel`, `Outreach.status` (`SPECS.md` §6). Email guesses are unverified and have no status enum. There is no `audience_type` enum: audiences are free text in the `audiences` table. Template vars are open: any lowercase `snake_case` name in `{{double_braces}}`, up to 50 per template, declared in `templates.placeholders` and filled in `outreaches.metadata` (`docs/features/templates/SPEC.md`, `docs/features/outreach/SPEC.md`).
- A dialog that edits a record and stays mounted must reset its form when it *opens*, never off the record prop. `useForm`'s `defaultValues` are read once at mount, so a `Dialog` that hides rather than unmounts shows whatever the record looked like when the page first rendered: the card behind it reads fresh from the query and shows the saved body while the textarea still holds the old one. Extract a `formDefaults(record)` function and call `reset(formDefaults(record))` in the `onOpenChange` handler. Keying it off the prop with a `useEffect` is the trap — a background refetch lands mid-edit and eats the user's typing. An always-mounted inline form with no open event uses react-hook-form's `values` prop instead (`notes-form.tsx`), which re-syncs only when the server value actually changes. Also await `invalidateQueries` after a write when another view's cached copy feeds a form: the compose dialog derives its entire field set from the shared `["templates"]` cache, which is `staleTime` old and fire-and-forget invalidation can leave stale.
- The same rule for non-form state: a soft navigation to another `:id` re-renders the page rather than remounting it, so a client subtree holding record-scoped `useState` (a draft the previous record's value would be written under, a poll-ceiling flag, a highlighted row) leaks across records. Key those subtrees on the record id — `key={target.id}` in `target-detail-page.tsx` — which resets every piece of internal state, cancels timers and drops in-flight mutations, with no effect and no reset plumbing. A no-op when the framework already remounts, a fix when it does not.
- DB tables and their Drizzle consts are always plural (`users`, `sessions`, `targets`); Better Auth model names map to them explicitly in `lib/auth.ts`.
- A target has three name columns but one fact. `full_name` is the name: required, the only one the add form asks for, the only one the UI displays. `first_name`/`last_name` are an override for names that do not split naively (`Bae Suzy`, `van der Berg`, `Cher`, `J. Smith`), null on most rows, entered only via the edit dialog's collapsed "Name for email patterns" section. Never ask a user to type the same fact three ways, and never keep a split in sync with the full name by copying between them: resolve it through `nameParts()` in `lib/target-name.ts`, which the email-guess worker and the `{{first_name}}` prefill both call so guessed addresses and greetings cannot disagree (`docs/features/targets/SPEC.md`).
- User-entered text can hold a pasted URL, which is one unbreakable token. Anywhere it renders, it needs `break-words` alongside `whitespace-pre-wrap`, and the element needs `min-w-0` (or the grid parent `grid-cols-[minmax(0,1fr)]`), or it widens its container instead of wrapping. This shipped as three separate overflow bugs: the compose review list, the target outreach history, and the whole dialog grid. Truncate with `truncate` (plus `flex-1` so it takes only the leftover space) where a value is a summary rather than body copy. The fourth was the template `<Select>`: the item text was `flex-1 shrink-0`, and a flex item will not shrink below its content, so `whitespace-nowrap` forced the row wider than the popup and clipped it hard instead of ellipsizing. `SelectItem`'s `ItemText` is now `min-w-0`, and long text (a template name) truncates in a child span, exactly as the trigger already did — so check the primitive, not just the call site, when a `Select` clips.
- Email pipeline order: `POST /api/targets` → `email-guess { targetId, userId }` → ranked, unverified `EmailGuess` rows. Only the owner sets `target.primary_email`; the worker never does. Workers are standalone Node processes, not in the Next.js server (`SPECS.md` §7–8; `docs/features/email-accuracy/SPEC.md`).
- List endpoints that grow are cursor-paginated through `lib/pagination.ts`, never with `offset`. Two traps this already caught: a keyset must be keyed on an **immutable** column (`outreaches` orders by `created_at`, not the status-rewritten `last_status_change_at`, or a status PATCH re-sorts the list mid-scroll and skips rows), and `created_at` alone is not a keyset — it needs the `id` tiebreaker for rows sharing a timestamp. In Valibot a schema `default` is validated as the schema's *input* type, so a `v.string()` pipe defaults to `"25"`, not `25`. List queries need an index whose leading columns match the predicate and sort; the `(user_id, created_at, id)` composites on `targets`/`outreaches` exist for exactly this and are scanned backwards for `DESC` (`docs/features/pagination/SPEC.md`).
- Build order: `docs/README.md`: foundation → auth → landing → targets/templates → outreach/email-pipeline. Don't build SaaS/billing/multi-region (`SPECS.md` §2.2, §11).
